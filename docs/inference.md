## Implemented Phase 1 components (local only)

`orchestrator/probe_plan.py` prepares inert canonical JSON for the fixed Vultr chat endpoint, one nonstreaming completion, no tools and a bounded completion count. Approved models and endpoint cannot be supplied by a user/model. A reviewed `RateQuote` binds model, integer micro-USD rates per million tokens, source-evidence hash and validity timestamps. Reservation uses a conservative full 262144-token input bound plus the requested output cap, rounded up to an integer micro-dollar. This is a Phase 1 probe bound, not permission to exceed the future product job limits. Prompt bytes, quote identity and cost are bound into the exact request hash. Quote authenticity and actual model parameter compatibility are not established by hashing or synthetic tests.

`db/phase1/001_budget.sql` is a one-time infrastructure migration, not a Phase 2 schema freeze. Configure exactly one trusted project account; no user-selected account or budget reset. Dispatcher can call reserve/claim only; reconciler can settle only; neither has table mutation rights. Project <=$150, inference <=$25, probe <=$2; probe consumes all three caps. Account-row locks serialize admission. Require READ COMMITTED, fsync and synchronous_commit=on; keep those durability settings through commit. Reserve binds UUID/hash/category/amount/deadline. Claim rechecks account and request expiry, transitions once to uncertain, and must commit successfully **before** external I/O. Lost acknowledgement is uncertain, never an automatic retry. Reconciliation records known actual charges with evidence; unknown usage retains the reservation indefinitely. An overrun is recorded in full and blocks further admission. An owner/admin remains privileged and cannot be treated as an untrusted model-facing role.

Fourteen real local PostgreSQL check groups and 18 synthetic planner tests passed; see [receipt](evidence/phase1-budget-postgres-2026-11-04.json). No provider call, secret loading, HTTP dispatcher, model success, per-job call/token enforcement, alerts, tax calculation, VM metering or cloud spending stop is implemented. The future dispatcher must bind the planner quote expiry to the ledger request deadline, recheck all billing/approval gates, commit its claim, then issue exactly that request. Test-only PostgreSQL image findings and production configuration remain open in [readiness](phase1-readiness.md).

## Budget-backed client implementation — Nov 4

`PostgresBudget` now uses pinned Psycopg 3.3.7, parameterized SQL, one configured account, READ COMMITTED, synchronous commits, fsync inspection and bounded connection/statement/lock timeouts. A fresh transaction must acknowledge commit before reserve/claim returns. TCP uses verify-full TLS; Unix sockets are used only within the trusted local fixture here. Driver errors expose fixed codes, no DSN/SQL diagnostic. Missing commit acknowledgement prevents dispatch.

`run_json_probe` is an internal function with no route, CLI or secret loader. It prepares the exact quote-bound plan, commits reserve and claim, then sends one HTTPS request to the fixed Vultr endpoint using HTTPX 0.28.1. TLS verification on, environment proxy/CA overrides off, no redirects or retries, one connection. A monotonic deadline (at most 60s and no later than quote expiry) covers database, transport and response; an explicit post-parse check covers synchronous parsing. Status/encoding failures do not consume or expose provider error bodies. Raw response cap 256 KiB; model content cap 64 KiB; JSON depth 32 and node count 8192; duplicate keys, nonfinite numbers, long integers, invalid UTF-8/surrogates and non-object content rejected. Exactly one matching-model assistant completion ending in stop is required; tool/refusal/truncated results fail. Provider-reported token counts are checked but are never billing settlement. Missing usage remains unknown. No result, including a valid JSON object, is proof of the probe's requested semantic answer or correct generated code.

The real local database integration separately observes the committed uncertain state before mock HTTP and proves failure/replay keeps the reservation. Mock responses are labeled; there is no fake-provider release switch. The remaining deployment composition must load host-only secrets, establish billing eligibility/current rates, authenticate the real model catalogue and persist request/result evidence; readiness remains 503. ## Database authentication and host credentials — Nov 4

This supersedes the earlier arbitrary-DSN/Unix-test-only composition. The Phase 1 database is on the control host, with **Unix sockets only**, a fixed database `proofflow_budget` and dispatcher login `pf_budget_login`. `BudgetConnection` requires SCRAM authentication from the server, fixes connection parameters and rejects every `PG*` environment setting before connecting. No service-file, password-file, TCP, proxy or alternate-account fallback. Unix sockets do not use TLS; this is not permission to disable TLS on a future network database. Every operation checks fsync and full_page_writes and uses durable READ COMMITTED transactions. [PostgreSQL connection documentation](https://www.postgresql.org/docs/18/libpq-connect.html) defines these authentication and connection controls.

`002_runtime_roles.sql` creates constrained runtime identities and removes public database access. Dispatcher receives only its existing reserve/claim functions; settlement login starts NOLOGIN and is never given to the provider process. It creates no password, project account or billing authorization. Reviewed [HBA](../infra/postgres/pg_hba.conf) permits local OS-postgres peer administration, SCRAM for the named application roles, then rejects everything else. The [server defaults](../infra/postgres/postgresql.conf) disable TCP, preserve durability and prevent SQL/parameter logging. The socket directory must be database-owned, not writable by the controller, with a dedicated socket-access group; mount only that directory into the controller. Never share PGDATA. No database socket or credential reaches the worker/verifier.

Setup after the cloud gate opens: initialize a new private data directory as PostgreSQL UID70 with `initdb --auth-local=peer --auth-host=reject`; install the reviewed configs before first service start; start the pinned database process as UID70 with read-only root, no capabilities, private bounded temporary storage and a persistent data volume. Apply 001 then 002 as the local peer administrator in `proofflow_budget`. Use interactive `psql` `\password pf_budget_login` in the protected operator terminal, or a reviewed secret-management channel; never place a password in SQL history, shell arguments, Git or chat. Store the matching database password and the later operator-created Vultr key as `budget-password` and `vultr-api-key` under `/etc/proofflow/credentials`, owned by the provider service UID, modes 0400/0600, ancestors root/service-owned and not group/world writable. Do not create an inference subscription until the existing billing gate passes. [PostgreSQL password guidance](https://www.postgresql.org/docs/18/auth-password.html) documents SCRAM and interactive password setup.

`load_provider_secrets` reads only those two fixed files, pins each ancestor and inode, rejects symlinks/hardlinks/FIFOs/devices, wrong owners/modes, oversized/non-ASCII/whitespace values and concurrent mutation, and closes descriptors on all paths. Secrets are excluded from repr/errors. It is Linux-only and accepts a single optional trailing LF. Loading secrets is not activation: no CLI, HTTP route, startup hook or paid request was added. Configure one durable account with blocked=true until eligibility, final costs and quote evidence are verified; do not create fresh accounts to reset usage. Credential revocation/rotation and secure deployment provisioning remain operational work; Python strings are not guaranteed to be zeroized.
