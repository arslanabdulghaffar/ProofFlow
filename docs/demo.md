# Demonstration and public explanation

Demo plan; implementation has started with the local trusted health foundation. No video, public app, customer result or benchmark exists. Goal: a useful working workflow early enough for people to try/share after public-release authorization. Early submission does not guarantee ranking, votes or judging advantage.

Current description: “ProofFlow is being built to repair supported revenue-import pipelines and expose the evidence behind each decision. A successful process can still assign revenue to the wrong merchant. We plan to check every record against approved rules before a repaired version can process the next batch.”

## Four-minute storyboard (timing target)

| Time | Real on-screen evidence | Meaning |
| --- | --- | --- |
| 0:00–0:25 | Original exits zero yet wrong merchant/customer record appears | Business error can be silent |
| 0:25–1:35 | Fresh compatible upload, explicit contract, real job/model request, stored diff, sandbox receipt | Required provider actually generates and runs code |
| 1:35–2:15 | Failed independent check then valid record evidence | A natural bad candidate is shown if it occurs; otherwise a separately labeled deliberate mutation tests the verifier |
| 2:15–2:50 | Exact approval, new batch event, fresh execution and durable checked output | Reusable version is different from one checked artifact |
| 2:50–3:15 | Harmless capped loop, deadline/cleanup receipt, healthy app | One measured containment boundary, not universal security proof |
| 3:15–4:00 | Evidence download, architecture, actual benchmark counts/costs/limits | Claims can be inspected |

Keep actual elapsed time visible; clearly disclose edits/replay and original timestamps. Never insert a stored patch as live inference or invent a rejected attempt. Preserve unedited run record and matching evidence. Rehearse the final release from a clean browser with three unseen variants and ambiguity; check readable UI, uploads, credits, downloads, App access and absence of secrets on screen.

Self-service judge path: guest workspace → labeled synthetic sample or compatible unseen upload → contract review → run → source/actual failure → candidate diff/receipt/checks → exact activation → fresh batch → download. Operator-only GitHub preview/readback is a separate real demonstration. Unsupported input explains its boundary instead of substituting a fixture. A failed live run remains failed; prior replay cannot substitute for working release gates.

Prior art includes Datafold migration/validation, Soda contracts, ADP-MA/AegisFlow remediation, and generic coding agents. Do not claim first self-healing pipeline. Differentiate only with implemented protected acceptance, useful per-record witness, containment, exact approvals and measured baseline comparison. “Why not deterministic ETL?” is answered with actual comparable results, including where D wins. No formal-proof/security-certification/customer-ROI claim. Optional human time baseline/interviews need actual consent and authorization; if unavailable, publish system latency only.

Submission copy/deck may use present-tense capabilities only after corresponding gates pass. Planned slides: user/error, live workflow, trust boundaries, independent verification, measured evaluation/baselines, value/limitations, team. Cover is 16:9; media limits must be checked against current form. Do not publish or contact prospective users from this plan alone.
